# API contract

Frozen before implementation. Do not change this contract without the lead updating both apps.

Base URL in development: `http://localhost:3001`. The Vite dev server proxies `/api` to that origin. JSON fields are camelCase.

## Runtime and setup

Supported runtime: **Node.js 26.13.1**, Active LTS, codename Lithium. `.nvmrc` pins that version. Both packages set `"engines": { "node": ">=26.13.1 <27" }`. Node 25 is not an LTS release and is not the supported runtime.

From the repository root, with nvm installed:

```bash
nvm install
nvm use
cp .env.example .env
docker compose up -d
until docker compose exec db pg_isready -U tasks -d tasks; do sleep 1; done
docker compose exec db psql -U tasks -d tasks -c "SELECT datname FROM pg_database WHERE datname IN ('tasks', 'tasks_test') ORDER BY datname;"
cd server
npm ci
npm run migrate
npm run migrate:test
npm test
npm run dev
```

In another shell, from `client`:

```bash
nvm use
npm ci
npm run dev
```

Open `http://localhost:5173`.

Environment loading:

- `cp .env.example .env` creates the root env file. Do not commit `.env`.
- Docker Compose, run from the repository root, substitutes variables from `.env`.
- Server scripts load it explicitly with Node: `node --env-file=../.env`. There is no dotenv dependency. A missing `.env` makes those scripts fail.
- `DATABASE_URL` is the development database `tasks`. `TEST_DATABASE_URL` is the dedicated database `tasks_test`. The application code must not fall back from one to the other.

PostgreSQL readiness and initialization:

- `docker compose up -d` starts Postgres 16. The published host port is `POSTGRES_PORT` (5434 in the example) so this project does not attach to another Postgres already listening on 5432 or 5433.
- `pg_isready` must succeed before migrations. The init script `docker/initdb/01-create-test-database.sql` runs only on a new volume, before the server accepts connections, and creates `tasks_test`. Schema is not created by that script.
- `npm run migrate` applies `server/migrations` to `DATABASE_URL` and aborts if that database name is `tasks_test`.
- `npm run migrate:test` applies the same migrations to `TEST_DATABASE_URL` after the test-database guard below.
- A clean database means `docker compose down -v` and then `docker compose up -d` again, followed by both migrate commands. `down -v` deletes local task data.

The API listens on `API_PORT` (3001). The client dev server listens on 5173.

## Task resource

```json
{
  "id": "2f4c1d2e-7b8a-4e1a-9c3d-6a5b4c3d2e1f",
  "title": "Ship task API",
  "description": null,
  "status": "TODO",
  "priority": "MEDIUM",
  "assignee": "Liam",
  "dueDate": "2026-11-20",
  "createdAt": "2026-11-18T09:00:00.000Z",
  "updatedAt": "2026-11-18T09:00:00.000Z"
}
```

- `id` is a UUID generated by Postgres `gen_random_uuid()`.
- `createdAt` and `updatedAt` are UTC timestamps generated by the database. Clients cannot set them.
- `dueDate` is a calendar date with no time and no timezone suffix.
- Postgres `DATE` values must be read as strings (`YYYY-MM-DD`). Do not use the default node-pg `Date` parser for OID 1082, because it can shift the calendar day.
- Status values: `TODO`, `IN_PROGRESS`, `DONE`.
- Priority values: `LOW`, `MEDIUM`, `HIGH`.

## Create

`POST /api/tasks` returns `201` and the task.

| Field | Rule |
| --- | --- |
| `title` | Required. Trim, then length 3–120. |
| `dueDate` | Required. Strict `YYYY-MM-DD`, a real calendar date, on or after the UTC date of the server clock. |
| `status` | Optional. Default `TODO`. Any of the three statuses is valid on create. |
| `priority` | Optional. Default `MEDIUM`. |
| `description` | Optional. Blank or omitted becomes `null`. Trim. Maximum 2000 characters. |
| `assignee` | Optional. Blank or omitted becomes `null`. Trim. Maximum 80 characters. |

Unknown fields are ignored and not stored. Creation writes no status-history row.

## Partial update

`PATCH /api/tasks/:id` returns `200` and the task. Omitted fields stay unchanged.

- `title`, `status`, `priority`, and `dueDate` cannot be set to `null`.
- `description` and `assignee` may be set to `null` to clear them. Blank strings become `null`.
- `{}` changes nothing, including `updatedAt`.
- `updatedAt` changes only when a stored field changes.
- An invalid status transition rejects the whole request. Other fields in that request are not saved.
- The past-date rule applies only when `dueDate` is different from the stored value. An omitted due date, or one equal to the stored value, skips that rule.

## Read and delete

- `GET /api/tasks/:id` returns `200` and the task.
- `DELETE /api/tasks/:id` returns `204` and an empty body.
- A path id that is not a UUID returns `400`. A UUID that does not exist returns `404`.

## Status history

`GET /api/tasks/:id/status-history` returns `200`:

```json
{
  "data": [
    {
      "id": "6b1c0a9e-1d2f-4a3b-8c7d-9e0f1a2b3c4d",
      "taskId": "2f4c1d2e-7b8a-4e1a-9c3d-6a5b4c3d2e1f",
      "previousStatus": "TODO",
      "newStatus": "IN_PROGRESS",
      "changedAt": "2026-11-18T10:00:00.000Z"
    }
  ]
}
```

Order by `changedAt` ascending, then history id ascending. No changes yet returns `{ "data": [] }`.

Each actual status change on update writes exactly one row, in the same transaction as the task update. The row stores the task id, previous status, new status, and timestamp. A same-status update writes no row. Creation writes no row.

Hard delete removes the task and, through `ON DELETE CASCADE`, its history. Status history exists for the lifetime of the task and is not retained after deletion. A later history request for that id returns `404`.

## List

`GET /api/tasks` returns `200`:

```json
{
  "data": [],
  "page": 1,
  "pageSize": 20,
  "total": 0,
  "totalPages": 0
}
```

Query parameters:

| Param | Rule |
| --- | --- |
| `status` | Optional enum. |
| `priority` | Optional enum. |
| `q` | Optional title substring. Blank or whitespace means no search. |
| `sort` | `dueDate` or `createdAt`. Default `dueDate`. |
| `order` | `asc` or `desc`. Default `asc`. |
| `page` | Integer. Default 1. Minimum 1. |
| `pageSize` | Integer. Default 20. Minimum 1. Maximum 50. |

Missing parameters use defaults. Present but invalid parameters return `400`. Do not coerce invalid values into defaults and do not clamp an out-of-range page size.

Invalid inputs, each a separate failure: `page=0`, `page=-1`, `page=1.5`, `page=abc`, `pageSize=0`, `pageSize=-1`, `pageSize=51`, `pageSize=abc`, an unknown `sort`, an unknown `order`, or an unknown enum. These are validation errors, not empty results.

A syntactically valid page past the end, such as `page=2` when the filtered total fits on page 1, returns `200`, `"data": []`, and the true `total` for the same filters. `totalPages` is `0` when `total` is `0`, otherwise `ceil(total / pageSize)`.

The same filters apply to the row query and the count query. Offset is `(page - 1) * pageSize`.

Sort allowlist, with direction chosen only from `ASC` or `DESC`:

- `dueDate`: `due_date <dir>, created_at ASC, id ASC`
- `createdAt`: `created_at <dir>, id ASC`

The tie-breakers stay ascending. Never interpolate the raw query string into `ORDER BY`.

Filters combine with AND. `q` is a case-insensitive literal substring of `title` only. It does not search the description.

### Title search escape

User text is bound as a parameter. Build the pattern in application code by escaping `\`, `%`, and `_`, then wrapping the escaped text in `%`.

SQL convention: `title ILIKE $n ESCAPE '\'`.

Escape rule, applied to every one of those three characters: prefix it with a backslash. The characters `%` and `_` added around the pattern are the only wildcards. A search for `%`, `_`, or `\` must match titles that contain that character and must not match every title.

## Dates and status rules

Today is the UTC calendar date of the injected clock, `YYYY-MM-DD` from `getUTCFullYear()`, `getUTCMonth()`, and `getUTCDate()`. At `2026-11-18T23:30:00.000Z`, today is `2026-11-18`. At `2026-11-19T00:30:00.000Z`, today is `2026-11-19`.

Reject dates that are not real calendar dates, including `2026-02-31` and `2025-02-29`. Accept `2024-02-29` when today is `2024-02-28` or earlier. Compare date strings only after validation. Reject a time component such as `2026-11-18T00:00:00Z`.

Create accepts today and rejects an earlier date.

Updates may move `TODO` to `IN_PROGRESS`, and `IN_PROGRESS` to `DONE`. The same status is valid. Skipping a step and moving backward are rejected. `DONE` may stay `DONE` and cannot move. The transition graph applies to updates only.

An overdue task remains editable. A title, description, priority, assignee, or legal status change succeeds when the request does not change `dueDate`. Sending the stored due date again also succeeds. Sending a different due date earlier than today fails, and nothing else in that request is saved.

The edit form omits an unchanged due date from `PATCH`.

## Concurrency and deletion

The update path uses one database client and one transaction:

1. `SELECT … FROM tasks WHERE id = $1 FOR UPDATE`.
2. Validate the patch against that locked row.
3. Update the task when a stored field changes.
4. Insert one history row when, and only when, the status changed.
5. Commit.

The row lock serializes concurrent status changes. The second transaction reads the status committed by the first. Two attempts to make the same status change therefore produce one history row. This keeps history consistent. It does not prevent lost updates of other fields. Two clients can each read a task, change different fields, and the later commit can overwrite the earlier one. Preventing that requires a version check or equivalent optimistic concurrency control. That check is intentionally not implemented.

Delete is a hard delete. History is removed with the task and exists only for the task's lifetime.

## Errors

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [
      { "field": "dueDate", "message": "Due date cannot be earlier than 2026-11-18 (UTC)" }
    ]
  }
}
```

- `400` `VALIDATION_ERROR` for a bad body, query, path, calendar date, or past due date. Include `details` for field errors.
- `404` `NOT_FOUND` with message `Task not found` when the task does not exist.
- `409` `INVALID_TRANSITION` when the status move is illegal. `details` contains field `status`. Example message: `Cannot change status from TODO to DONE`.
- `500` `INTERNAL_ERROR` with a generic message. Do not return stack traces, SQL, or connection strings.
- Malformed JSON uses the same `400` error shape.

Illegal transition example:

```json
{
  "error": {
    "code": "INVALID_TRANSITION",
    "message": "Cannot change status from TODO to DONE",
    "details": [
      { "field": "status", "message": "Allowed transition is TODO to IN_PROGRESS" }
    ]
  }
}
```

## Test database guard

Before any test migration or any statement that truncates or deletes rows in the test runner, call one shared guard. It must abort the process when any of these are true:

- `TEST_DATABASE_URL` is missing or blank.
- `TEST_DATABASE_URL` is not a Postgres URL with a database name.
- The database name is anything other than `tasks_test`.
- `DATABASE_URL` is set and its database name is also `tasks_test`, or the two URLs identify the same database.

The guard must not invent a default URL. Development migrate uses `DATABASE_URL` only and refuses `tasks_test`. Test migrate and tests use `TEST_DATABASE_URL` only after the guard.

Tests that share `tasks_test` and truncate it run serially. Vitest must set `fileParallelism: false`, `maxWorkers: 1`, and `sequence.concurrent: false`. Truncate inside the test process only after the guard. Use `TRUNCATE tasks RESTART IDENTITY CASCADE` so history rows are removed with their tasks between tests.

The API under test receives the guarded test URL and a fixed clock. Do not use the machine clock for date assertions.

Required automated coverage:

- Title trimming and length, enums, blank optional fields, and ignored unknown fields.
- Create defaults, explicit initial `DONE` with an empty history, and rejected past or impossible dates.
- UTC today just before and just after midnight.
- Leap-day acceptance and impossible dates such as `2024-02-30` and `2025-02-29`.
- An adjacent transition writes one history row. The same status writes none. A skip or reverse transition returns `409`, writes no history, and leaves every field unchanged.
- An overdue task accepts a title change and an equal due date, and rejects a changed past due date.
- Combined status and priority filters, title search, sort order, tie-break, and matching totals.
- Literal searches for `%`, `_`, and `\`, proving those characters are not wildcards.
- Invalid `page` and `pageSize` inputs return `400`, in separate cases from a valid page past the end.
- A valid page past the end returns `200`, an empty `data` array, and the true total.
- Two concurrent requests that apply the same status change produce exactly one history row.
- Delete returns `204`. Later get and history requests return `404`, and the history rows are gone.
